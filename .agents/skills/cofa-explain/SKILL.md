# 작업 설명 노트

목표는 **내가 한 일을 내 말로 설명할 수 있게 되는 것**이다. 문장을 외우는 게 아니라, 무엇을 왜 그렇게 했는지 이해하는 것이다.

## 1. 근거
`INTERVIEW.md`, `AGREEMENT.md`, `PLAN.md`, `FLOW.md`, `DECISIONS.md`, `VERIFICATION.md`, `HANDOFF.md`, README가 요구한 문서, `git log --oneline`, 핵심 코드 파일·함수 이름만 본다.
기록에 없는 일은 쓰지 않는다. 비어 있는 주제는 "아직 없음: ___하면 생김"이라고 적는다.

## 2. EXPLAIN.md 주제 (내 작업의 실제 이름을 넣는다)
1. **고른 방식**: 무엇을 골랐고, 왜, 다른 방식과 무엇이 다르고, 그래서 무엇을 내려놓았나
2. **요청 흐름**: 버튼을 누른 뒤 결과가 저장될 때까지 어떤 단계와 파일을 거치고, 각 단계가 무엇을 맡고 데이터는 어디에 있나
3. **범위와 확인 위치**: 만든 것, 만들지 않은 것(가정과 한계), 그걸 확인할 수 있는 파일과 테스트
4. **이상 상황**: 잘못된 파일, 빠진 기록, 극단값, AI 실패일 때 실제로 무엇이 나오나
5. **위험과 확인 방법**: 결과가 틀릴 수 있는 곳, 그런 입력, 직접 해 본 확인이나 실험과 그 결과
6. **AI와 함께 한 과정**: 내가 고친 사례 하나를 순서대로 (계기 → 내 요청 → AI 제안 → 받아들인 것·바꾼 것·뺀 것 → 근거 → 확인)
7. **담당자 말 → 결과물**: 담당자의 어떤 말이 어떤 기능이나 화면이 됐나, 그리고 **그 말을 어떤 질문으로 끌어냈나** (처음 요청 → 내가 물은 것 → 담당자 답 → 나온 조건. `INTERVIEW.md`의 꼬리 질문 사례 하나)

주제마다 이 모양으로 쓴다. 문장은 짧게, 요점 위주로.
```
## 1. 고른 방식
- 요점: [3~5개 단어]
- 설명:
  - 무엇: ___
  - 왜: 담당자가 "___"라고 해서(Q_) ___
  - 다른 방식과 차이: ___
  - 내려놓은 것: ___
- 근거: [D번호, 파일·함수, 테스트 이름]
```
사용자는 개발자가 아니다. 코드 문법이 아니라 **역할 수준**(이 파일이 무엇을 받아 무엇을 하고 어디로 넘기나)으로 쓰고, 사용자가 세부를 모르는 부분은 "AI가 작성, 나는 ___로 확인" 형태로 쓴다. 파일·함수·테스트 이름은 정확히 쓴다.
맨 아래에 "흐름 한 줄"을 붙인다: `[입력] → [검사: 파일] → [계산: 파일] → [저장: 어디] → [표시: 파일]`

## 3. 설명 점검
"EXPLAIN.md를 3분 읽고 닫으세요. 몇 가지 여쭤볼게요."라고 말한다.
주제 1, 2(시간이 있으면 6)에 대해 하나씩 묻고, 사용자가 **자기 말로 쓴 설명**을 받는다. 노트 내용을 먼저 보여 주지 않는다.
피드백 3줄 이내: 빠진 부분, 실제 작업과 다른 곳, 덧붙이면 좋을 한 가지.
설명이 막히는 주제가 있으면 그 부분의 코드나 기록을 쉬운 말로 다시 풀어 준다.
