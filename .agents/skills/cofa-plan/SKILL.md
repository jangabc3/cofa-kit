# 구현 계획

코드를 쓰기 전에 `PLAN.md`를 쓰고, 사용자에게 보여 준 뒤 OK를 받는다. OK 전에는 파일을 만들지 않는다.

## 먼저 확인
- 쓸 수 있는 런타임: `node --version`, `python3 --version`
- OpenAI 환경변수가 있는지만 확인한다 (값은 출력하지 않는다): `[ -n "$OPENAI_API_KEY" ] && echo 있음`
- 남은 시간 (사용자에게 묻는다)

## PLAN.md 형식
```
# 계획

## 한 줄 요약
## 구조
- 기술: (가장 단순한 것. 예: Python 표준 라이브러리 서버 + HTML 한 장, 또는 Node + Express)
- 화면: (화면 이름과 그 화면에서 하는 일)
- 데이터: (어디서 읽고 어디에 저장하나)
## 화면 흐름 (3단계 이내)
- 사용자: [누가, 어디서, 무엇으로, 얼마 동안]
- 흐름: ① [첫 행동] → ② [다음 행동] → ③ [결과를 보고 하는 일]
- 화면에 영향을 주는 담당자 조건: [예: 장갑 → 큰 버튼, 5분 → 한 화면 요약] (Q번호)
- 화면 다듬기는 핵심 기능이 된 뒤 `$cofa-ux`로 한다.
## 기능 요구사항
| 번호 | 기능 (사용자가 할 수 있는 것) | 근거 | 확인 방법 |
| FR-1 | (예: 원인 미확정 문의에서 사실/조사 중을 나눈 초안을 받는다) | Q2 | (예: 원인 없는 예시로 단정 표현이 없는지) |
## 핵심 방식 고르기 (사용자가 고른다)
| | 방식 A (가장 단순) | 방식 B | 방식 C (가장 정교) |
| 어떻게 | (쉬운 말 한 줄) | | (예: 모든 경우를 다 따져 보는 최적화) |
| 좋은 점 | | | |
| 대가 | | | |
| 시간 안에 되나 | | | |
- 추천: (하나) — 이유 한 줄. **사용자가 고르기 전에는 확정하지 않는다.** "단순하게"라는 요청은 구조를 단순하게 하라는 뜻이지 방식을 대신 고르라는 뜻이 아니다. 표를 보여 주고 "어느 방식으로 할까요?"라고 묻고 멈춘다.
- 세 방식 모두 **합의문의 "이번에 만들 것"과 조건을 다 지켜야 한다.** 합의된 기능(예: 엑셀 입력)을 빼는 안은 방식이 아니라 범위 변경이므로 표에 넣지 않는다. 범위를 줄여야 하면 따로 "범위 줄이기 제안"으로 쓰고 담당자 합의가 필요하다고 적는다.
- 고른 뒤 `DECISIONS.md`에: 고른 방식, 이유(담당자 말), 버린 대안과 차이, **포기한 것**.
## 요청 흐름 (FLOW.md 초안)
사용자가 버튼을 누른 뒤 결과가 저장될 때까지의 단계를 표로 쓴다. 코드가 생기면 실제 파일 이름으로 고친다.
| 단계 | 하는 일 (쉬운 말) | 파일·함수 | 데이터를 가진 곳 |
| 1 입력 | 화면에서 값을 받는다 | | 브라우저 |
| 2 검사 | 잘못된 값을 막는다 | | |
| 3 계산 | 규칙대로 결과를 만든다 | | |
| 4 저장 | | | (파일/메모리) |
| 5 표시 | | | |
## 고정 코드로 할 일과 LLM에 맡길 일
| 할 일 | 방식 | 이유 |
## 위험과 대비
- (LLM 실패, 느린 응답, 잘못된 입력, 빈 데이터 등)
## 시제품 속 AI 지시문 (LLM 기능이 있을 때)
- 근거: 넘겨준 자료만 쓴다. 자료에 없으면 "확인 필요"로 표시하고 추측하지 않는다.
- 출처: 문장이나 항목마다 근거(행 번호, 파일, 항목 이름)를 붙인다.
- 형식: 정해진 JSON으로 받고, 형식이 틀리면 대체 동작으로 간다.
- 보내기 전 처리: 민감 정보는 코드로 가린 뒤 보낸다. 무엇을 가리는지 적는다.
## 작업 목록
1. [ ] (15~30분 크기. 어떤 FR을 만드는지 적고, "확인 방법"을 붙인다. 예: 작업 1 — FR-1, FR-2)
## 시간표
- 핵심 기능 하나 끝까지: ~ 남은 시간의 50%
- 확장: ~ 25%
- 검증과 문서: 최소 25%
```

## 원칙
- 기능 요구사항은 합의문의 "이번에 만들 것"과 "지켜야 할 조건"에서만 나온다. 근거 칸에는 담당자 질문 번호(Q3)나 합의문 항목을 적고, 근거가 없는 기능은 넣지 않는다.
- FR은 3~6개로 둔다. 별도의 PRD나 FRD 문서는 만들지 않는다. 합의문이 PRD, 이 표가 FRD 역할을 한다.
- 핵심 방식은 사용자가 **설명할 수 있는 것**을 우선한다. 정교한 방식은 시간과 설명 부담이 크면 대안으로만 적는다.
- 요청 흐름은 `FLOW.md`로 따로 저장한다 (README가 다른 이름을 요구하면 그 문서에 넣는다).
- 첫 작업은 핵심 흐름 하나가 화면부터 결과까지 이어지는 가장 얇은 버전이다.
- 합의문의 "만들지 않을 것"은 계획에 넣지 않는다.
- 사용자가 계획을 바꾸면 PLAN.md를 고치고 `DECISIONS.md`에 이유를 남긴다.
